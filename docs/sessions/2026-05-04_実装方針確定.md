# 2026-05-04 実装方針確定

ntfy.sh 動作確認後の本格設計セッション。バックエンド技術スタック・MVP スコープ・ブランディング方針を確定し、Claude Code hooks / Cloudflare Workers / FCM v1 / Android 通知アクションの仕様を網羅的に監査した。

## 確定事項

### スコープ
- 個人利用のみ。Play Store 等への配布なし
- public repo として GitHub 公開
- MVP = **Stop/Notification の通知 + PreToolUse の Approve/Deny 遠隔操作**
- 端末は Android 1 台 + Fitbit ミラー（first-responder-wins だが実質 1 台運用）
- ウィジェット系は future work（[`../widget-plan.md`](../widget-plan.md)）

### 技術選定

| レイヤ | 採用 | 理由 |
|---|---|---|
| Android | Kotlin + Compose | 既定 |
| バックエンド言語 | Node (TypeScript) | ユーザー指定 |
| バックエンド配置 | **Cloudflare Workers** | 常時 0 円圏、コールドスタートなし、edge 配信、user 既存利用あり |
| ストレージ | **D1** (SQLite at edge) | Sequential Consistency、ポーリング設計に必要 |
| HTTP フレームワーク | Hono | Workers ネイティブ + Express 風 |
| 通知配送 | FCM v1 | Workers の Web Crypto で RS256 JWT 署名可 |

### 候補から外した選択肢

- **Cloud Run**: scale-to-zero でコールドスタート 1〜2 秒、min instances=1 にすると月数ドル課金。Workers の方が体感・コスト共に上。「Node そのままで書きたい」要件が強ければ再検討の余地はある
- **Vercel/Netlify Functions**: 関数タイムアウトが短い（10〜60 秒）。今回はポーリング設計で各 req は短いので使える可能性はあるが、長時間 hook block 等の将来オプションを潰すので回避
- **KV (Cloudflare)**: eventual consistency で最大 60 秒の伝搬遅延。スマホ Approve → PC poll の到達が遅延しうる
- **Durable Objects**: 強整合性は出るが Workers Paid プラン必要（月 $5〜）。MVP には過剰
- **localhost backend + Tailscale**: 「ローカル常時起動はやりたくない」要件と逆行

### ブランディング
- アプリアイコンは Claude Code 公式マスコット **Clawd**（公式名、タコ／カニ的なピクセルアート）を意識した独自イラスト
- Anthropic 知財は商用利用しない範囲で類似させるに留め、公式素材そのものは repo にコミットしない

## 設計監査結果

### Claude Code hooks 仕様（公式 docs 確認）

- **PreToolUse stdin**: `{session_id, cwd, transcript_path, permission_mode, hook_event_name, tool_name, tool_input, tool_use_id}`
- **PreToolUse stdout** (exit 0):
  ```json
  {
    "hookSpecificOutput": {
      "hookEventName": "PreToolUse",
      "permissionDecision": "allow|deny|ask|defer",
      "permissionDecisionReason": "..."
    }
  }
  ```
- **デフォルトタイムアウト**: コマンド型 hook = **600 秒**。人間の応答に十分余裕がある（私の前回発言「60 秒」は誤り）
- **`ask` の活用**: hook 内ポーリングがタイムアウトしたら `ask` を返すことで Claude Code の通常承認プロンプトに fallback できる。スマホ未応答時の救済として有効
- **複数 hook の優先度**: `deny > defer > ask > allow`
- **matcher**: 正規表現で tool 名を絞れる。すべてではなく `Bash|Edit|Write|MultiEdit|mcp__.*` 等に絞ることで通知過多を回避
- **exit code**: `0` = JSON output 処理 / `2` = blocking error / その他 = non-blocking error

### Cloudflare Workers + D1 + FCM v1 の組み合わせ可否

- **Workers の Web Crypto API で RS256 JWT 署名可** → FCM v1 service account 認証通る（参考: `sagi/workers-jwt`）
- **D1 は Sequential Consistency**（"read your own writes"）。スマホ Approve 直後の PC poll で確実に最新値が読める
- **D1 read replicas は opt-in**（Sessions API 使用時）、デフォルトは primary 単独で十分
- **Workers 無料枠**: 100,000 req/day, D1 reads 5M/day, D1 writes 100k/day。本プロジェクト想定消費量（~17,000 req/day）の **6 倍以上の余裕**

### Android FCM 通知アクション

- **data-only message** で送信（FCM payload に `notification` フィールドなし、`data` のみ）
- アプリの `FirebaseMessagingService.onMessageReceived()` で `NotificationCompat.Builder` を組み立て、`addAction()` で Approve/Deny ボタンを追加
- 各アクションは `PendingIntent` → `BroadcastReceiver` → backend POST。**アプリ起動なしで承認完結**
- FCM トークンは `onNewToken()` で更新通知 → backend に再登録

### 認証・秘匿情報の扱い

- **共有秘密 bearer token** 1 種類で PC hook ↔ backend ↔ Android アプリ の三方向認証を兼ねる
- 32 bytes 暗号学的ランダム文字列を 1 度だけ生成し、3 箇所に配置（PC、Android、Workers secret）
- public repo にはコードのみ、`.env.example` で必要 secret を明示
- FCM service account JSON も Workers secret として注入

### ポーリング設計の妥当性

- 1 秒間隔 × 最大 5 分 = 最大 300 req/承認
- 想定: 50 承認/日 × 平均 30 秒（60 polls） + 100 通知/日 + その他 ≈ **17,000 req/日**
- Workers 無料枠（100k/日）の 17%、十分余裕
- アイドル時 0 req（リクエスト課金）、ポーリング中も Workers が握り続けるわけではない（短い req の連続）

## 監査で見つけた設計改善点

| 元案 | 変更後 | 理由 |
|---|---|---|
| KV で承認状態管理 | **D1 に変更** | KV は eventual consistency で最大 60 秒の伝搬遅延 |
| hook タイムアウト時の挙動未定義 | **`ask` を返して通常プロンプトに fallback** | スマホ未応答時に Claude Code が固まらない |
| 全 tool に対し hook 起動 | **matcher で `Bash\|Edit\|Write\|MultiEdit\|mcp__.*` に限定** | Read 等の安全 tool まで通知すると過多 |
| long-poll / SSE で hook block | **短い HTTP polling（1秒間隔）** | Workers との相性最良、長時間 HTTP 不要に |
