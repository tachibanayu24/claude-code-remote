# 2026-05-13 CLI 即答時の mobile 通知抑制

`ask_delay_ms` (デフォルト 10s) より前に CLI で permission に answer した場合、mobile に push が飛ばないようにした。`channel.mjs` が JSONL を見て「CC が当該 prompt の先に進んだ」を検知 → backend を expire → notify をキャンセル、という素直な経路を 1 本通した。

## 動機

旧設計では PostToolUse hook が `/v1/hook/posttool` 経由で `dismissPendingApprovals` を呼んでキャンセルしていたが、PostToolUse はツール完了後にしか発火しない。CLI で即 allow した Bash が 30s 走ると、`ask_delay_ms = 10s` 経過時点ではまだツール実行中で row は pending のまま → FCM 発火。デフォルト挙動として「答えたのに鳴る」が頻発していた。

## アプローチ A 採用 (B/C は不採用)

検討した 3 案:

- **A. JSONL の `tool_result` を見て dismiss**: channel.mjs が既に JSONL を読んでいるので 1 箇所つなぐだけ。新概念ゼロ
- **B. data-only サイレント FCM → ask_delay 経過時に可視通知へ昇格**: FCM channel 二系統 + Android 側 state machine + delay の意味語変更が必要
- **C. ask_delay の動的切替**: 既存設定の UX 改善で済むが根本解決ではない

設計的素直さで A が圧勝なので A を採用。長時間 Bash の allow (>10s) は `tool_result` が間に合わず救えないが、これは「CC が実際に走っている間は phone に出ても害がない」という解釈で許容範囲。

## 実装

### `hooks/lib/jsonl.mjs` (新規関数 2 つ)

- `findPendingToolUseInJsonl(jsonl, toolName, inputPreview)`: tool_name + input 一致の最新 `tool_use` ブロックで、まだ `tool_result` が付いていないものを返す。input 完全一致を優先、なければ name 一致の最新を fallback
- `hasToolResultFor(jsonl, toolUseId)`: 指定 id への `tool_result` 存在を返す
- 補助の `deepEqualJson` も同居 (key 順序の揺らぎを吸収)

### `channel/channel.mjs`

- `permission_request` 受信時に JSONL を読んで `toolUseId` を `pendingApprovals` エントリに同梱。CC が tool_use を書く前に notification が来た race のために defer (null) も許容
- `setTimeout` の handle を `entry.notifyTimer` に保存
- 新ヘルパー `maybeDismissFromJsonl(backendId, entry)`: `tool_result` が出ていたら `/v1/approvals/:id/dismiss` を叩き、`notifyTimer` を `clearTimeout`、`pendingApprovals` から除去
- 呼び出しは 2 箇所:
  - **wait ループの毎回**: early-dismiss 路。inflight 中は 5s 周期で回るので CLI answer から数秒で消える
  - **`/notify` の setTimeout 内、`/notify` 呼ぶ直前**: 最終ガード。wait ループ最後のポールと timer 発火の race を埋める
- `handleVerdictEvent` と `sweepExpiredPending` でも `notifyTimer` を `clearTimeout`

### `backend`

- `db.ts`: `dismissApprovalById(db, env, id)` を追加。`RETURNING` で 1 行 expire、`notifyApprovalResolved(decision:'expired', resolved_by:'cli')` を fan-out
- `routes/approvals.ts`: `POST /:id/dismiss` ルートを追加。`/v1/hook/posttool` の単行版という位置付け
- Android 側は既存の `approval_resolved` (`decision:'expired'`) ハンドラがそのまま使えるので無改修

## 検証

- `tsc --noEmit` クリーン
- `node --check` クリーン
- 本番 deploy 後の curl smoke: 存在しない id を `/dismiss` → `{"ok":true,"dismissed":false}` HTTP 200

## 残課題

- `findPendingToolUseInJsonl` は同 turn で同 tool が同 input で複数回呼ばれた場合、tool_use_id を取り違える可能性がある (最新の pending を取るので、後勝ち)。実害は薄いが将来同 prompt 内で連発したときに表面化しうる
- 長時間ツールの allow (>`ask_delay_ms`) は依然として鳴る。気になるなら `ask_delay_ms` を伸ばすか、Phase 2 で B 路線 (data-only → 昇格) を検討
