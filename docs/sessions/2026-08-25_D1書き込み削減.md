# 2026-08-25 D1 書き込み削減 (heartbeat throttle + index drop + bye)

## 背景

Cloudflare から D1 無料プラン制限 (2026-09-01 適用開始) の超過警告。計測の結果、
アカウント書き込み超過 (日次 10 万行、直近 31 日中 15 日超過、最大 228,405 行/日) の
ほぼ 100% がこの repo の D1 だった。

内訳 (d1 insights、直近 7 日):

- 総書き込み 564,928 行のうち 564,015 行が `wait.ts` 冒頭の heartbeat UPSERT
  (188,005 回 × 3 行)
- 3 行/回 = 本体 1 + secondary index 2 本 (idx_sessions_heartbeat, idx_sessions_cwd)。
  D1 は index への書き込みも rows_written 1 行と数える
- /v1/wait は channel.mjs から 5s (inflight) / 15s (idle) 周期で叩かれ、毎回無条件に
  UPSERT していた
- 読み取りは日次最大 84 万行 (制限 500 万) で問題なし

## 対策 (3 本柱)

### 1. heartbeat UPSERT の変化検知 + throttle (backend/src/routes/wait.ts)

UPSERT 前に row を SELECT (読み取りは桁違いに安いのでトレード) し、以下のときだけ書く:

- row が無い → 即 write
- 状態遷移フィールド (cwd / 非空 ai_title / current_prompt) が変化 → 即 write。
  phone の working/idle バッジと detail 入力バーの正準シグナルなので遅延させない
- in-flight snapshot (current_blocks / jsonl_mtime) だけの変化 → 前回 write から
  `SNAPSHOT_MIN_GAP_SEC` (20s) 以上のときだけ。detail のライブ進捗が ~5s → ~20s lag
- 無変化 → `HEARTBEAT_KEEPALIVE_SEC` (60s) ごとの純粋な生存通知のみ

server 側で判定するので、稼働中の channel.mjs (長寿命プロセス) も deploy 直後から
即座に恩恵を受ける (channel 再起動不要)。

### 2. sessions の secondary index 2 本を drop (migration 0018)

sessions は高々数十 row (生存分 + stale cleanup までの 7 日分)。full scan で十分で、
idx_sessions_cwd に至っては 0010 の per-session 化以降 cwd で引く query 自体が無い。
書き込みコスト 3 行/回 → 1 行/回。

### 3. TTL 引き上げ + graceful bye (sessions.ts / channel.mjs)

keepalive 60s に対し `SESSION_HEARTBEAT_TTL_SEC` を 90 → 180 に引き上げ
(keepalive 60s + wait 1 round ≤15s + エラー backoff 1 回 ≤30s に余裕)。
crash 検出が最長 3 分になる代償は `POST /v1/sessions/:sid/bye` で相殺:
channel.mjs が終了時 (stdin EOF / SIGTERM / SIGHUP / close event の SIGTERM 送信後) に
best-effort (fire-once, 1.5s cap) で bye を送り、last_heartbeat を TTL より過去に倒して
即 closed 表示にする。graceful 終了はむしろ従来 (最長 90s) より速く closed になる。

bye は close_requested_at も NULL に掃除する — marker が立ったまま終了すると
`claude --continue` 再開直後の初回 /v1/wait で close が再発火して即死するため
(既知の即死バグ族の残穴を 1 つ塞いだ)。

close event 受信時は channel.mjs が `closing` フラグで waitLoop を止め、bye で倒した
row を自分の heartbeat で蘇生させないようにする。

## Android 30s TTL 問題とサーバ側クランプ

`SessionDetailScreen.kt` の `SESSION_LIVE_TTL_SEC = 30` が detail の `last_heartbeat`
生値と端末時計を比較して入力バーの活性を決めており、書き込みを 60s 間隔にすると
生存中でも入力バーが死ぬ。アプリ改修 (rebuild は user 主導) を避けるため、detail
レスポンスの `last_heartbeat` を「生存中 (server TTL 内) なら now にクランプ、死後は
生値」に意味変更した。旧アプリのまま正しく動き、端末とサーバの clock skew 依存も消えた。

## 効果 (見積もり + 本番実測)

- idle セッション: 5,760 writes/日 × 3 行 = 17k 行/日 → 1,440 × 1 行 = 1.4k 行/日
- inflight 連続稼働: 17k × 3 = 52k 行/日 → ~4.3k × 1 行 = 4.3k 行/日
- 合計で従来比 ~1/12〜1/36。平均 8.3 万行/日 → 数千行/日のオーダー、ヘビー日でも
  他 DB (計 ~1 万行/日) と合算して 10 万行/日制限に大幅な余裕
- deploy 後の本番実測: idle セッションは 35s 間で書き込み 0 回 (従来 15s ごと)、
  inflight セッションは 35s 間で 1 回 (従来 5s ごと)

## 応答性への影響 (現状維持を確認)

- prompt 配送 / approval verdict / close 検出: /v1/wait の内側 D1 poll (2s) が担って
  おり heartbeat 書き込み頻度と独立 — 影響なし (smoke test で確認)
- turn 開始 (working 遷移): current_prompt 変化は即 write — 従来同等
- turn 終了 (idle 遷移): Stop hook の UPDATE 経由 — 変更なし
- detail のライブ進捗 (current_blocks): ~5s lag → 最大 ~20s lag (唯一の劣化、許容)
- 一覧の closed 検出: graceful 終了は bye で即時 (従来最長 90s より改善)、
  crash/スリープ時のみ最長 3 分 (従来 90s)

## 検証

- ローカル (wrangler dev + d1 --local) で throttle 全分岐・クランプ・bye・蘇生・
  close single-fire を curl で smoke test、全パス
- 本番 deploy (worker 8ba37d6c) + migration 0018 remote 適用後、実セッションの
  last_heartbeat 進行間隔で throttle 発効を確認

## 残メモ

- channel.mjs の bye は channel 再起動後のセッションから有効 (稼働中の旧 channel は
  TTL 180s fallback で closed になる)
- Android は無改修。将来 detail の liveness をきちんとやるなら `heartbeat_age_sec` を
  detail にも載せて「fetch 時 age + 経過時間 < TTL」に置き換えるのが筋 (任意)
- 一覧の「idle · Xs ago」表示は keepalive 間隔ぶん (最大 ~1m) 粗くなった (表示のみ)
