# 2026-05-14 全体リファクタリング (backend approval ドメイン抽出 + channel.mjs 分割)

CLI 即答時の通知抑制を入れたあと、backend と channel の両方を「fat モジュール解消・責務分離・重複削減」観点で監査し、コミット 2 本にまとめてリファクタした。デプロイ済み、push 済み。

## 監査

各モジュールの行数と中身を全件読んで、以下の判断基準で見た:

- 単一責任で説明できるか
- 公開 API は呼び出し側の語彙か (実装語彙ではないか)
- 同じパターンが 2 箇所以上にあって SoT が曖昧か
- 抽象化したらむしろ追いづらくないか

### 抽象化を「見送った」もの

判断は積極的 (一部リファクタ案を不採用):

- `types.ts` (118 行): domain 別分割は時期尚早。1 ファイルで grep しやすい
- `jsonl.mjs` (378 行): cohesion 高、各 parser は内部状態を持たない関数なので分けるメリット < grep しやすさのコスト
- `routes/hooks.ts` の stop ハンドラ (~90 行): 各ステップが明確で名前がついているので関数分割しても可読性が上がらない
- `push.ts` の 3 つの notify\* 関数: union 型 1 関数にすると call site の意図が読み取りづらくなる
- `cc-remote-hook.mjs` の stop ポーリング: 単一 use site

「過度な抽象化」の予防が今回のテーマで、特に **channel.mjs から `pending state machine` と `event handlers` をさらに切り出すかどうか**は迷ったが、`mcp`/`apiPost`/`pendingApprovals`/`log` への依存をモジュール境界越しに引き回すと「お互い参照しあう anaemic モジュール」が量産されるので止めた。本体 400 行で「MCP server + wait loop + state machine」が一覧できる粒度を維持する方針。

## コミット 1: refactor(backend) — approval ドメインを集約

3 箇所に散らばっていた tool_input JSON blob のパースと SQL/通知ペアの重複を `backend/src/approvals.ts` に集約。

### 抽出した API

- `parseToolInputBlob(raw)` / `encodeToolInputBlob(b)`: `approvals.tool_input` D1 カラムの decode/encode。defaults 込み (旧 row 互換)
- `approvalPushData(args)`: FCM の `approval_request` data payload を構築。POST `/` (即時 push) と POST `/:id/notify` (delay 後 push) の二箇所で同じ shape を組み立てていた
- `supportsAlwaysDefault(v)`: 旧 channel.mjs 互換 (フラグ無し → true)
- `dismissPendingApprovals(db, env, sessionId)`: PostToolUse hook 経路
- `dismissApprovalById(db, env, id)`: channel.mjs 早期 dismiss 経路
- 内部 `expirePendingApprovals(db, env, where, value)`: 上記 2 関数の SQL/通知が完全に同型だったので `where: 'session_id' | 'id'` リテラル union で DRY 化。文字列補間は user 入力ではないので injection 無し

### 影響範囲

- `routes/approvals.ts`: 2 箇所の payload 構築重複を解消。`parseToolInputBlob`/`encodeToolInputBlob`/`approvalPushData` に集約
- `routes/sessions.ts`: GET `/:sid/turns` の pending_approvals 整形で同じ JSON.parse を再実装していた → `parseToolInputBlob` 1 行に
- `routes/hooks.ts`: import path だけ変更 (`db` → `approvals`)
- `db.ts`: approval 関連を全部抜いたので 90 → 30 行。`nowSec` + cleanup + `readJson` の generic ヘルパーだけ残った

deploy 後の smoke test: `/dismiss` `/sessions` `/settings` を curl で叩いて HTTP 200 + 期待スキーマ確認済み。

## コミット 2: refactor(channel) — 関心ごとに分割

`channel.mjs` 535 行 → 399 行。3 つの submodule に分離。

### `channel/lib/api.mjs` (29 行)

- env から `BACKEND` / `SECRET` 読み込み → module-private に格納
- `isConfigured()`: bool 公開
- `apiPost(path, payload, signal)`: bearer + content-type 付き fetch

config を channel.mjs から完全に追い出して、本体は `isConfigured()` で gate するだけ。 BACKEND/SECRET の export 自体を辞めたので「設定値が外でいじられる」恐れが消えた。

### `channel/lib/session.mjs` (85 行)

- `readPpidSession()`: `~/.claude/sessions/<ppid>.json` を読んで `{sessionId, cwd}` を返す
- `getSessionLabel()`: ai-title を 5s TTL でキャッシュ。module-private な labelCache を関数に閉じ込め
- `inspectSession()`: heartbeat snapshot を組み立てる (current_prompt + current_blocks の inflight 判定込み)

CC との接合面 (ppid → sessionId → jsonl path) を 1 ファイルに固めた。channel.mjs 本体から JSONL の読み方を 1 段隠せた。

### `channel/lib/allowlist.mjs` (78 行)

- `deriveAllowPattern(toolName, inputPreview)`: Bash/WebFetch の許可パターン生成。SoT
- `appendAllowPattern(cwd, pattern, log?)`: tmp + rename の原子的書き込み。logger は optional (default no-op) なので importer 単体テストも楽

CC `/permissions add` との同時書き込み race の説明を JSDoc に集約。

### channel.mjs 本体の変更

- `inspectSession()` で読んだ JSONL とは別に、wait ループの early-dismiss 経路で **pending 全件分の JSONL を毎回読み直していた N 回 I/O を 1 回読みに統合**。`maybeDismissFromJsonl(backendId, entry, jsonl?)` で optional 引数として受け取る形に変更
- `notifyTimer` の `clearTimeout` が `sweepExpiredPending` / `maybeDismissFromJsonl` / `handleVerdictEvent` の 3 箇所に散らばっていた → `clearPending(backendId)` 1 関数に一元化。timer の lifecycle が読みやすくなった
- `mcp.notification` を出す処理と `pendingApprovals.delete` の対応関係を `clearPending` でセットに

## 残った将来の課題 (メモ)

リファクタ範囲外として手は付けなかった:

- `findPendingToolUseInJsonl` が同 turn で同 tool が同 input で複数回呼ばれた場合、tool_use_id を取り違える可能性 (latest 取りの fallback パス)
- 長時間ツールの allow (>`ask_delay_ms`) は依然として鳴る。Phase 2 で data-only → 昇格方式を入れるなら別腹
- `routes/wait.ts` の heartbeat upsert が長め (~30 行のクエリ)。SQL を `const HEARTBEAT_UPSERT_SQL = \`...\`` に切り出すかは趣味の範囲、見送り
- channel の `handlePromptEvent` / `handleVerdictEvent` を `lib/events.mjs` に切り出すかは保留 (mcp, apiPost, state map への依存が多くて、抽出すると param-pass か state injection が要る)
